# Roadmap

Проект находится на стабильной ветке 4.x. Этот документ описывает только
дальнейшие работы; реализованное состояние зафиксировано в
[`IMPLEMENTATION_PLAN.md`](IMPLEMENTATION_PLAN.md), а пользовательские сценарии —
в [`README.md`](README.md) и на сайте документации.

## P0 — воспроизводимая базовая версия Music Assistant

Текущий код использует новый API плагинов Music Assistant: `AudioSource`, setup
values и методы актуального `PluginProvider`. Зафиксированная в `uv.lock` версия
Music Assistant отстаёт от этого API, поэтому чистая установка окружения не
может собрать все тесты и mypy без внешней корректировки зависимостей.

- синхронизировать git-ревизии `music-assistant` и `music-assistant-models` с
  минимально поддерживаемой версией API;
- зафиксировать совместимую пару зависимостей в lock-файле;
- добавить проверку чистой установки в CI;
- после этого считать полный `pytest` и `mypy` обязательными release gates.

## P1 — интеграционное покрытие

- проверять setup flow с несколькими экземплярами `yandex_music`;
- покрыть жизненный цикл `AudioSource`: выбор, смену трека, паузу, seek и stop;
- добавить сценарии обрыва WebSocket, обновления токена и восстановления сессии;
- проверить длинные radio/wave-сессии и пополнение очереди на реальных ответах
  API, очищенных от персональных данных;
- тестировать согласование PCM-формата с возможностями разных типов плееров.

## P1 — декомпозиция провайдера

`provider/provider.py` объединяет координацию сессии, управление плеером,
потоковую передачу, метаданные и пополнение очереди. Следующий рефакторинг
должен выделить эти обязанности в небольшие компоненты без изменения внешнего
поведения и формата конфигурации.

## P2 — улучшения Music Assistant upstream

Некоторые ограничения нельзя корректно решить только внутри провайдера:

- отображение всей цепочки сигнала и реального PCM-формата в интерфейсе;
- отображение внешней очереди Ynison рядом с текущим треком;
- более явные состояния восстановления внешнего источника;
- унифицированные возможности управления для `AudioSource`-провайдеров.

Такие изменения требуют согласования с моделями, сервером и frontend Music
Assistant и должны начинаться с отдельного upstream RFC.

## P2 — самостоятельная библиотека `ya-ynison`

После стабилизации протокольного слоя можно вынести WebSocket-клиент и модели в
отдельный пакет без зависимостей от Music Assistant. До этого необходимо:

- заменить framework-исключения собственными типами;
- определить стабильный публичный API клиента;
- собрать набор записанных протокольных контрактов;
- обеспечить отдельные CI, версионирование и публикацию пакета.

## P3 — несколько источников на экземпляр

Сейчас один экземпляр провайдера публикует один `AudioSource`; несколько
аккаунтов или устройств настраиваются отдельными экземплярами. Поддержку
нескольких источников в одном экземпляре стоит рассматривать только после
появления устойчивого серверного API и понятного пользовательского сценария.
